- **RELAY-SOURCES-02 (September 19 findings):** Miami's provider entry address redirects across a rotating pool of six same-provider destinations; the preview allowlist held five, producing intermittent relay 502s at the unlisted destination's share (about one request in six). The sixth exact origin was added to the private preview catalog; a bounded client retry already covers a single unlisted roll, and any future pool growth fails closed the same way. Virginia Tech's replay host answers a recording's first cold request with a signed redirect to a separately approved origin, so cold archive HEAD/GET failed closed; `archiveConfig.redirectOrigins` now carries that exact origin. That same VT replay host also returned 503/521 directly for most of its recordings during checks while its sibling host was fully healthy, and the VT live source returned 502 directly; both remain provider availability, not relay faults. Duke, WSJS, WCCG, WTIB, both custom ports and Miami passed 300-second transport runs on the native path.
- **RELAY-FREE-01 progress:** Version-isolated `wrangler tail` CPU on the deployed native preview version: 63 invocations across catalog, live, archive and HLS-game routes all at 2–8 ms, median 4 ms; 30-, 120- and 300-second live streams each cost 3–5 ms for the whole invocation, so CPU no longer grows with listening time. Cold-start isolation, a real maximum playlist and account-wide daily usage at listener scale remain unmeasured.
- **RELAY-HLS-01 progress (September 19, Georgia Tech live):** The first real Homestream playlist failed closed on a `+0000` timestamp offset, fixed in 9678b78. The provider serves one-second segments in a 350-entry window (31 KB, no encryption, no master), and the initial per-segment capability rewrite produced a 242 KB playlist at 25–66 ms CPU per reload; directory capabilities with relative names restored provider size at p50 4 / p99 14 ms over 90 one-second reloads with 0 errors, segments p50 1 / p99 3 ms. A simulated listener consumes about 112 MB/hour of playlist and 65 MB/hour of audio at that window, identical to direct provider consumption. Remaining: master/variant, AES key and byte-range paths against a real provider that uses them, Sync timestamp seeking in a browser, and phone playback.
- **SYNC-RECOVER-01 (found September 19, not fixed):** `SyncPlayer` restarts from the entry after a fatal player error with 1/2/4-second waits, but `recovery.attempts` is never reset after a successful reconnect, so the fourth fatal error over a long session stops playback with "The stream stopped" even when each earlier reconnect worked. Reset the counter after sustained playback (for example 60 seconds of `playing`).
- **SYNC-RECOVER-02 (found September 19, not fixed):** a reconnect restarts at the live edge and asks the listener to "check alignment", discarding the delay they set. Record the playing program date before the restart and seek back to it once the new level is loaded, falling back to the live edge only when that timestamp is outside the window. Server-side, game capabilities now last six hours and expired ones answer 403, so expiry no longer causes this during a game; provider hiccups still do.
